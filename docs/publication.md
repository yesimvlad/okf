# Как публиковать знания Yesim

GitHub — место для исходников, истории и проверки изменений. Для публичного поиска основные проверенные материалы стоит разместить на официальном домене Yesim. Наличие репозитория, OKF или llms.txt само по себе не означает обучение модели, индексацию, цитирование или рекомендацию бренда.

## Предлагаемые адреса

Это план размещения; адреса `/knowledge/` ещё не опубликованы на сайте.

| Материал | Предлагаемое размещение | Назначение |
|---|---|---|
| Основной справочник EN | `https://yesim.app/knowledge/` | Видимая HTML-страница с определением продукта и навигацией |
| Отдельные справки | `/knowledge/products/esim.html`, `/knowledge/faq/activation.html` и другие адреса сборки | Ответы о продукте, инструкциях и ограничениях |
| Чистый Markdown | Те же справки с расширением `.md` | Чтение агентами и загрузка в инструменты с файлами |
| OKF с происхождением и датами | `/knowledge/okf/` | Потребители, которым нужны метаданные доверия и связей |
| Короткий указатель | `/knowledge/llms.txt`; ссылка из существующего корневого `/llms.txt` | Навигация по проверенным материалам |
| Manifest | `/knowledge/manifest.json` | Состав, даты, источники и контрольные суммы выгрузки |
| Sitemap | `/knowledge/sitemap.xml`; включение в основной sitemap | Обнаружение HTML-страниц поисковыми системами |
| Редакционные исследования | GitHub, `internal/seo/` и `competitors/` | Работа контент-команды; исключены из публичной сборки |

Поле `generated` необязательно в базовой спецификации OKF: постоянно обязательным является `type`. В профиле этого репозитория происхождение, источники и даты обязательны для проверки публикации. Поэтому `generated` сохранено в исходниках и машинной OKF-версии; YAML-таблица не показывается в чистом Markdown и HTML. Дата проверки источников и срок повторной проверки остаются доступны. Это машинная проверка публичных источников, а не подпись сотрудника Product/Legal.

## Сборка для разработчиков

Python 3.11 или новее:

```bash
python -m pip install -r requirements.txt
python scripts/validate.py
python -m unittest discover -s tests -v
python scripts/export_public.py --out dist/okf-release
python scripts/export_site.py --out dist/site-release --base-url https://yesim.app/knowledge/
python scripts/check_site.py dist/site-release --report dist/site-release/local-check.json
```

Каталог назначения должен быть новым или пустым. Сборка сайта создаёт статический HTML, чистый Markdown, машинную OKF-копию, llms.txt, manifest и sitemap. Она не подключается к CMS, хостингу или DNS и ничего не публикует сама. GitHub Actions сохраняет сборку как артефакт для разработчиков.

Публиковать нужно **содержимое `dist/site-release`**, а не весь репозиторий. Загрузку выполнять атомарно после проверки состава и содержимого. Если EN устарел или не прошёл правила публикации, сборка останавливается. Уже размещённые файлы сами не исчезают по достижении даты `stale_after`: команда сайта должна отслеживать сроки, повторно проверять источники и заменять или отзывать просроченные материалы. Изменение даты без проверки не считается обновлением.

## Первые действия

1. Источники оплаты, возвратов, конфиденциальности, Pay & Fly и Day Pass уже перепроверены. EN и 15 локализаций имеют автоматическую проверку фактов и языка. Это не подпись носителя языка или сотрудника Product/Legal. См. [финальный отчёт](final-source-and-publication-review.md).
2. Разработчики берут артефакт **yesim-reviewed-knowledge** из успешного запуска GitHub Actions и размещают **содержимое `dist/site/`** под `https://yesim.app/knowledge/`. При ручной сборке используют содержимое `dist/site-release/`. Репозиторий целиком размещать не нужно. Сейчас `/knowledge/`, EN HTML и указатель возвращают 404; в этой работе нет подключения к CMS/хостингу Yesim.
3. Сервер выдаёт HTML как `text/html; charset=utf-8`, Markdown как `text/markdown` либо `text/plain; charset=utf-8`, llms.txt как `text/plain`, manifest как `application/json`, sitemap как XML. Проверяют HTTPS, отсутствие входа/cookie-wall и содержимое без JavaScript. Canonical HTML — собственный опубликованный адрес. Для Markdown при необходимости добавляют HTTP Link с canonical на HTML; стратегия индексации машинных копий согласуется отдельно от доступа к ним.
4. SEO добавляет ссылки на справки из страниц продукта и Help Center, подключает `/knowledge/sitemap.xml` к основному sitemap и обновляет существующий корневой llms.txt по текущему составу продуктов. Сохраняют полезные языковые ссылки и добавляют `/knowledge/llms.txt`. Производственные title/description Pay & Fly и спорные гарантии исправляют в CMS по фактам из сборки.
5. Локальные HTML/Markdown EN + `ar`, `zh-cn`, `id`, `ru`, `pt`, `pt-br`, `es`, `it`, `cs`, `ja`, `fr`, `de`, `vi`, `pl`, `ro` готовы в сборке по профилю автоматической проверки. Каждая локализация имеет нативное представление из 17 вопросов и полный исходник в OKF. Ещё 28 языковых карточек остаются черновыми и не публикуются как полноценные переводы. Данные языка, проживания, цены/валюты и доступности оплаты не смешивают.
6. После размещения выполняют команду ниже и отдельно смотрят реальные логи роботов/CDN, robots.txt и фактические внутренние ссылки сайта. Allow в robots.txt и пробный User-Agent не доказывают обход реальным роботом. Последующее моделирование проводят отдельно без поиска, с пакетом и с веб-поиском.

```bash
python scripts/check_site.py dist/site-release --remote --report dist/site-release/deployment-check.json
```

При проверке артефакта Actions вместо `dist/site-release` используют путь к распакованному `dist/site`. До размещения live-проверка должна показать отсутствие EN-страницы, а не ложное успешное завершение. Скрипт проверяет HTTP, MIME, canonical и HTML/noindex; сохраняет robots для отдельной проверки. Он не воспроизводит реальные сети роботов и не удостоверяет правила CDN.

## Разметка и доступ

Сборка использует `WebPage`/`CollectionPage` для самих справочных страниц. Это не каталог коммерческих предложений. На настоящих продуктовых страницах разработчики могут использовать `Organization`, подходящий `Product` или `Service`, а `Offer` — только с ценой, валютой и условиями из актуального каталога. `@id` должны быть согласованы между страницами. Разметка должна соответствовать видимому тексту; не создавайте фиктивные рейтинги, цены, списки устройств или гарантии.

`llms.txt` — предложение для навигации, не управление доступом. Современная версия предложения рекомендует ссылки на Markdown через `rel="alternate" type="text/markdown"` и на указатель через `rel="describedby"`; сборка добавляет их в HTML. Их использование конкретным потребителем нужно проверять.

Политики доступа поисковых и других ботов определяются отдельно в robots/CDN. Google прямо указывает, что для AI Overviews и AI Mode не нужны специальные AI-файлы или особая Schema.org-разметка. Нужны доступный текст, внутренние ссылки, возможность обхода и соответствие разметки содержимому. Это объясняет приоритет HTML и исправления исходных страниц.

## Что остаётся за пределами сборки

- Нет авторизованного подключения к production CMS или инфраструктуре Yesim в рамках этой ревизии.
- Выполнен live-аудит 219 выбранных адресов и проверены взаимные hreflang сборки. Полный граф hreflang всего сайта, настоящий доступ ботов через CDN, checkout/приложение, человеческое нативное согласование и публичный LLM-бенчмарк не заявлены.
- Реальные тарифные ID, цены, операторы, списки устройств и функции отдельных номерных SKU должны поступать из системы продукта; схема связей не создаёт эти данные.
- Публичный GitHub не делает `internal/seo/` конфиденциальным. Если исследования станут закрытыми, перенесите их в приватный репозиторий.
- Для материалов Yesim ещё нужно выбрать правила повторного использования. Лицензия приложенной спецификации не лицензирует автоматически весь контент Yesim.
